# ADR-4737: Rolled surges recur each round through a nullable repeat_round key

A taunt, a rally and a hurt ally can each surge the same player character round after round, but every older surge kind is once per encounter and `DramaticSurgeRecord` enforced that with unique constraints that already exist in production. We added a nullable `repeat_round` column that the three rolled kinds fill with the encounter's round number (a check constraint pins it equal to `round_number`, and a second one makes a row either rolled, with both `repeat_round` and an `outcome`, or older, with neither), rewrote the two subject-keyed once-per-encounter constraints so they apply only where `repeat_round` is null, and added one merged unique constraint over the rows where it is set (`nulls_distinct=False`, so two subject-less rows in the same round collide the way two rows for the same subject do). A rolled kind therefore surges once per round per subject and the other kinds still surge once per encounter; the boss and companion constraints are untouched because a third check constraint keeps boss and companion subjects out of rolled rows. One NPC taunt per player character per round is the intended consequence: an NPC taunt carries no subject, so a second NPC taunt on the same character in a round neither rolls nor spends anything.

The rejected alternatives were reusing the once-per-encounter constraints, which would let a rolled kind surge only once in the whole fight, and a separate table for rolled surges, which would split the one write path (`apply_dramatic_surge`) and the one round payload that read every surge from one place. Two alternatives for the authored side were weighed and set aside. Reusing `Consequence` / `ConsequenceEffect` (the checks app) to map an outcome to a result would have given the outcome-to-effect mapping for free, but it has no effect type for engagement intensity or control, so it would have needed new effect types and a second route into the same engagement fields; a `SurgeTuning` with a `SurgeDegreeBand` per outcome is the narrower fit. Reusing `EscalationCurve`'s pace fields would have put the tuning on a per-encounter row, but a rolled surge is tuned globally per kind, and a curve cannot soften or sharpen one kind without also moving the pace it already drives. The price is a nullable discriminator column, three check constraints on the record, and a rolled surge that is inert until staff author a `SurgeTuning` row per kind with bands.

Two shapes differ from the parent spec's schema sketch. `taunt_potency` lives on the `ThreatPoolEntry`, not on the opponent template, because the pool entry is what an opponent actually does and carries its own line. And a player character taunting another sets the target's difficulty from the taunter's check rating for the Taunt check type, with no dice and nothing spent: an owner ruling of 2026-10-27, not a rolled result, so the taunter's standing is what the target resists. A second owner ruling of the same day has the surged player, GMs and staff read a cause line on each rolled surge instead of the generic "X surges." line, so the record keeps a `cause` text column written with the surge (a persona-named sentence, or the opponent's authored taunt text exactly as the room is told it); every other viewer keeps the generic line and sees no roll, bond or cause.

**Amendment (#4739, slice 3 of #4727).** An emotional condition feeds intensity every round through the same seam: `apply_condition_intensity_surges` (`world/combat/condition_surges.py`) writes one `CONDITION_FED` record per player character per round, after the escalation tick and only in an encounter with a curve, for the plain sum of `current_stage.intensity_per_round` over the character's active, unsuppressed, unresolved conditions (nothing for a sum of 0; NPC opponents never). It sets `repeat_round` but has no roll, so `surge_rolled_has_round_and_outcome` gained one narrow third branch: `repeat_round` set with no `outcome` is allowed only for `CONDITION_FED`. The rejected alternative was a synthetic outcome on every feed row, which would have shown players a roll that never happened. Because a feeding condition is a benefit, `validate_surge_bands` treats it as one (a better outcome may carry it where a worse one does not, and may not drop one a worse outcome carries) and refuses it on any band whose outcome has success level below 1: emotional conditions come only from a success or a choice.

# ADR-4373-A: A named NPC's standoff group reads its persona live and stamps nothing on it

A named NPC (a `Persona`) can stand as an opponent, from a beat's opponent line or the GM's Add Opponent, and then forms its own `StandoffGroup` (`persona` set; uniqueness is encounter, template, persona). Its `CombatOpponent.objectdb` is the NPC's own character, which outlives the encounter. So, unlike a creature (ADR-4361-A), nothing standoff-specific is written on that object: `stamp_opponent` skips drives for a persona opponent, and the group's drives are read live from `Persona.properties`, each at one fixed strength (`PERSONA_DRIVE_STRENGTH`, Major), because that relation carries no strength and the owner ruled that a named NPC's drives are authored there with no new form. Cause, margin, affiliation and switched-off rules are still stamped on the opponent row, which is per-encounter. A named NPC line therefore refuses drive edits (`PERSONA_DRIVE_EDIT_ERROR`). The NPC's `NpcRegard` for the acting character's presented persona enters the shared difficulty function as its caller-supplied base, one band per `StandoffConfig.regard_per_band` points, at most `regard_max_bands` (ADR-4145-B); the player sees only the direction, the GM the value. We rejected stamping the persona's properties as `ObjectProperty` rows on its character, because those rows would persist past the encounter and every other system reading the NPC's object properties would see standoff drives. We rejected a per-opponent drive table for this one case, for the reason ADR-4361-A gives. We rejected a strength per persona property, because it needs a through model on a shared scenes relation for one consumer; a fixed strength can become authored later without changing group identity.

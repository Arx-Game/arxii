# ADR-3657: The test suite is three layers, journeys, fuzz and cross-system, never coverage

The suite protects three things, in order: a journey per thing a player or staff member does, driven on the seam they reach it by (the real command handler through `JourneyCase.telnet`, `dispatch_player_action` through `JourneyCase.web`, the REST client) and asserting what the game told them; fuzz at those same seams with Hypothesis; and cross-system integration where one app's change breaks another. A unit test is kept only where a journey cannot reach the logic. Journeys are PostgreSQL-only by construction, because they cross the partitioned `Interaction` table and the materialized views the SQLite tier does not build. The journey inventory is generated from the code's registries (`tools/journey_inventory.py`) and pruned by hand into `docs/testing/journeys.md`; a per-app ledger (`tools/test_ledger.py`) proposes a layer per module and a person confirms every removal by naming the journey that still asserts the behaviour. Coverage is measured under the journey layer alone, as the detector of code no journey reaches, and is never a gate or a target. We rejected keeping the per-layer unit shape (`django_notes.md` prescribed a model, serializer, viewset and permission class per model, and 32,000 tests accreted in it while a command that never parsed its switches stayed green, #4352); a coverage percentage as the goal (it rewards the shape that hides breaks); fuzzing without a dependency (table-driven boundary cases protect less and cost the same); and writing the journey list from memory (the registries already enumerate what a user can do, and memory misses).

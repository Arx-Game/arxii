# ADR-4354-A: A standoff proposal is a GM decision prompt, and GM-run is derived

In a scene a GM is running, a standoff cause that fires does not start the fight: the group goes `PROPOSED` and the GM gets a `STANDOFF_CAUSE` prompt in the one GM prompt queue (`GMPrompt`, ADR-4101), with a `standoff_group` link, to Confirm (they attack), Hold for one action, or Override with a reason. Whether a standoff is GM-run is derived at the moment the cause fires, from the same `prompt_recipients` question every prompt source asks (the scene is active and has a GM who has not muted the `STANDOFF` group), never stored, so a GM stepping into a mission's scene takes over its next decision and a GM who mutes standoffs hands it back to the automatic path. `STANDOFF_CAUSE` is a new "decision" prompt kind: addressed to one GM like a narration prompt, so the visibility and per-GM copy rules are shared, but resolved by its own three actions, not narrated or dismissed, since it carries no authored default text to release. We rejected a separate proposal model and rail, because it would duplicate the queue's routing, muting, scene-end expiry and telnet listing; we rejected a stored "GM-run" flag on the encounter, because it would go stale the moment a GM joins or mutes; and we rejected a free-form GM outcome on a proposal, keeping to ADR-0110's bounded rulings. An override is remembered as the force on both sides when it was given, so the cause stays quiet until force moves or a botch lands, with no counter or timer.

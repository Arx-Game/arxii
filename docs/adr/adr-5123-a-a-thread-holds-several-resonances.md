# ADR-5123-A: A thread holds several resonances, and each pulled thread names the resonance that pays

A thread belonged to exactly one resonance, so a character with a main drive and a second one that complicates it could not put both into the thing they had bonded with. A thread now holds several: `ThreadResonance` rows (`thread`, `resonance`, `amount`) under it, one thread per anchor (the five uniqueness constraints keyed on resonance became `(owner, target)`, and weaving on a taken anchor is refused with a pointer to imbuing it). `amount` is the **cumulative** resonance of that kind ever imbued, never reduced when a level-up spends `developed_points`; the spec's first wording, "the rows sum to `developed_points`", was wrong because level-ups consume the points, and proportional draining would have made "largest" meaningless. Rows change only by imbue (add), the retune rite (move between rows) and the Fall and Redemption (scale and move), and a row that empties is deleted unless it is the thread's only one. `Thread.resonance` stays as a denormalized copy of the **leading** resonance (largest amount, a tie to the row created first), written only by `refresh_leading_resonance`, which every row writer calls: about 75 readers want "what the thread is", several of them ORM filters, locks and tier-0 handler keys that a derived property would turn into a subquery each. Each pulled thread names the **paying resonance**, chosen by the player each pull (`CombatPullThread` and `ScenePullThread` carry `paying_resonance`, a FK to `Resonance` and not to `ThreadResonance`, since a held resonance with no row may pay and then gives the ordinary pull benefit and no perks). The payer is charged the pull's cost and its perks are the ones applied: the leading resonance reads the thread's level, a resonance with a row reads `second_resonance_level_step` levels lower (never so low that `thread_level_multiplier`, which is not monotonic below level 10, lets it beat the leader), and only the leading resonance gives always-on tier-0 perks. This partly supersedes ADR-0052 (a gift's resonance is its woven thread's resonance: now its leading one, with the full set on the rows; `gift_resonances_for` returns the rows in order) and ADR-5066-B (each thread pays from its own resonance: now from its chosen payer, defaulting to the leader). **Rejected:** keeping one thread per (resonance, anchor) and letting a character stack threads (the bond with one thing would be several objects, a gift would need a picker for which thread casts, and a mixed thread could never read as one thing); deriving the leader on read (cheap to say, a subquery at every filter site); one payer per pull instead of per thread (contradicts "each thread pays for itself"); a minimum share before a second resonance counts (ruled none); and a second resonance reading the thread's full level (a 70/30 thread would out-perk a pure one, and the anti-goal is the opposite: a mixed thread never feels weaker than a pure one, and a second resonance never beats the leader).

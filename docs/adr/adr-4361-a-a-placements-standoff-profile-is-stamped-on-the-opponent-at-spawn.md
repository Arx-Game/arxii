# ADR-4361-A: A placement's standoff profile is stamped on the opponent at spawn

A placement (a beat's or a mission option's opponent line) may change its creature template's cause, cause margin and affiliation, raise, lower, remove or add drives, and switch off inherited faction rules. When the line spawns, each opponent is stamped with the result: `CombatOpponent.cause`, `cause_margin_percent`, `organization` and `suppressed_faction_rules`, and every drive as an `ObjectProperty` on the opponent's object with the strength as its value. A live standoff reads only that snapshot (`standoffs/services/profile.py`), so a placement's edits apply and a later edit to the template never changes a running encounter. Because a placement can add a drive the template lacks, a drive reveal now names the drive's `Property` instead of a `CreatureDrive` row (migrations 0230 to 0232, play state carried across). A group is still one template in one encounter; its profile is its first-spawned member's, so two differently edited placements of one template in the same encounter share the first one's profile. Faction rules are not copied: an opponent carries its template's rules plus those inherited through its stamped affiliation (the organization, each `parent_org`, each of their societies), read when needed, and where two matched rules shift the same thing only the most specific owner's count. We rejected reading the template live with per-line overrides layered on at read time, because every read site would need the line, and an opponent added by a GM or a later template edit would silently change a fight in progress. We rejected a dedicated per-opponent drive table, because drives are properties and the `Application` catalog already aims approaches at properties through `ObjectProperty`. We rejected one group per placement, because slice 3 changes group identity for named NPCs and the shared-profile case is rare.

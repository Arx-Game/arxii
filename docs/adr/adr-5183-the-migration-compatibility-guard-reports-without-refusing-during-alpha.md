# ADR-5183: The migration compatibility guard reports without refusing during alpha

The deploy runs migrations while the previous release is still serving, then reloads. #5159 added `tools/check_release_safety.py` as a gate before the migrate step: any pending migration that does more than create tables or indexes, or add nullable or database-defaulted columns, is refused unless its file carries a `# release-safety:` comment naming a commit already running on production. In effect this requires every column drop to ship one release after the code that stopped using the column. Nothing at authoring time or in CI checks for the comment, and within a day three PRs had merged twelve unmarked migrations (0447 to 0458), six of which drop columns or delete rows in the same release as their code change and so could not truthfully be marked. The production deploy of 2026-11-17 was refused before any migration ran. The owner ruled the same day that the two-release rule is how it should work once production holds play state that cannot be reset, and is superfluous before then. The gate therefore stays in the deploy and always runs, and its findings are printed in the deploy log, but it fails the play only when `app_release_safety_enforce` (in `infra/ansible/roles/app_deploy/defaults/main.yml`, `false` during alpha) is on.

**Consequences.** During alpha a migration needs no release-safety comment, and a drop may ship with its code change. For the seconds between the migrate step and the reload, and for longer if a reload fails, the old release can error on a table whose shape changed; the recovery path is the dump taken before every migration, and alpha play state is resettable (ADR-0237). Authored content keeps its own protection, which this does not touch: a migration that drops an authored column still declares its data disposition in the PR. Leaving alpha means setting `app_release_safety_enforce` to true, and from that deploy on the rules in `docs/operations/observability-baseline.md` section 4.5 apply as written.

**Rejected:** rewriting the twelve unapplied migrations into an add-only release and a later drop release (a large rework, and every development database that had applied them would need repair, to protect tables that hold no rows); a one-off deploy option that stops the server before migrating (a control whose purpose nobody would remember); and reverting #5159 (the check is correct for a production with durable play state, and keeping it running in report-only form shows what it would refuse before it matters).

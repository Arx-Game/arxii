# ADR-3055: The beta cutover reserves original characters with the roster fields they already have

The owner ruled on 2026-08-07 that roster tenures end at the beta cutover, that roster characters go back to Available with their progress wiped, and that a player's original character may be reserved to its creator instead of deleted. The spec placed the reservation on `CharacterSheet.is_oc`, which ADR-0317 retired. An original character is now `RosterEntry.creation_provenance == PLAYER`, and `created_by_account` records who authored it (character creation writes both for every player-made entry). The cutover reserves with those two fields and adds no column, table or flag: an original character with a recorded author may only be applied for by that account, enforced in `RosterApplicationCreateSerializer` and in the `can_apply` flag through `is_reserved_against`. The wipe leaves the entry on the Available shelf with its tenure ended, and the creator re-enters through the ordinary application, which re-seats them on their own past tenure. A separate reservation flag was rejected because it would be a second copy of a fact the provenance fields already hold, and the two could disagree.

Two ordering rules follow from the ledger design (ADR-0206). The policy steps (end tenures, return to Available, progress-reset each kept character) run before the wipe, because the progress reset reads the play-time `CharacterTraitChange` rows and class-level receipts the wipe deletes, and both run in one transaction behind the four guards of ADR-0207. The progress reset derives a trait baseline as the current value minus the sum of the play-time deltas rather than replaying rows in order, so interleaved authoring changes and a level reversal's own logged corrections cannot double count.

**Consequences.** The rule is general, not cutover-only: from the cutover on, an original character can only ever be claimed by its creator, and a staff handover has to change `creation_provenance` first. Every character a tester made in character creation is an original character with an author, so reservation covers almost all of the alpha population automatically; `--carry-over` exists for the rest. An original character with no recorded author is not reserved and not touched by the policy steps. Who deletes the alpha characters that match none of the policy kinds is not decided here.

**Rejected:** a `reserved_for` column on `RosterEntry`; keeping alpha tenures and asking players to re-confirm; and putting the progress reset inside the wipe, which would reverse ledger rows the wipe had already deleted.

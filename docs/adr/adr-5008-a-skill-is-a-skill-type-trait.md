# ADR-5008: A skill is a skill-type Trait, and Skill is its proxy

A skill used to be a `Trait` of type SKILL plus a companion `Skill` row holding its tooltip, sheet order, active flag and specializations, with a second rating store (`CharacterSkillValue`, the #4496 "one rating, two stores" contract) and a second development and rust ledger, so nobody could say in one sentence what `Skill` was for and staff authored a skill across two forms. The owner's test settled it: a profile row exists only to extend a row we cannot modify (Evennia's), and `Trait` is ours, so the `Skill` table was folded into `Trait` (`tooltip`, `display_order`, `is_active`) and dropped, the rating is the trait's `CharacterTraitValue` and the progress its `DevelopmentPoints` row (#5010). `Skill` survives as a Django proxy of `Trait` (owner, #5015): a typed view with no table, whose manager shows only skill-type traits, so every FK to a skill still says `Skill` and the code keeps its vocabulary while the column holds a trait pk. The proxy shares `Trait`'s identity map, so skill behaviour lives on `Trait`. The fold was an ADR-0237 restructure, expand, copy and contract in three migrations (`0376` to `0378`), with a copy step that reverses. We rejected FKs to `Trait` with `limit_choices_to` (a larger diff that loses the Skill name), renaming `Skill` to a profile model (it keeps the "a skill is this plus that" explanation alive) and keeping the second rating store (two copies drift, #4496). `species.Language` has the same companion shape on LANGUAGE traits and is deliberately untouched.

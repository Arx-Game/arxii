## Unresolved findings

- **[Severe] The Look dialog self-closes ~150-200ms after opening, from both the right-click and left-click triggers.** Confirmed independent of network/data-loading timing: delaying the mocked dispatch response by 1500ms did not keep the dialog open past ~200ms, so this is not a "content swapped in, focus moved" race — it reproduces before the look text even arrives. This defeats Decision 1 and the entirety of Screens 2/2b's promise (drag to read, close deliberately): a real player sees the dialog flash open and vanish before they can read the result, drag it, or press Esc/×. Consistent with a known Radix composition hazard: `LookDialog`'s `Dialog.Root` is `modal={false}` (`frontend/src/game/persona-menu/LookDialog.tsx:50`) and is opened synchronously from a Radix `ContextMenuItem`/`DropdownMenuItem`'s `onClick` (`frontend/src/scenes/components/PersonaMenu.tsx:565`, `handleLook`); the closing menu's own focus-restoration lands on an element outside the new non-modal Dialog shortly after, which the Dialog's `DismissableLayer` treats as an outside interaction and dismisses. Not caught by the PR's own `PersonaMenu.test.tsx:284-309` because jsdom does not reproduce this real-browser focus-timing interaction — this is exactly the class of defect a component/unit test cannot see and a rendered-browser demo-fidelity review exists to catch. Suggested mechanical companion: a Playwright assertion (in whichever e2e suite eventually covers `/game`) that the Look dialog is still `visible` after a fixed real-time wait (e.g. 500ms) following the menu click, with no further interaction — the shape this class of Radix modal/menu composition bug takes is exactly "passes an immediate assertion, fails a delayed one," so the test has to include the wait to be worth anything.
- **[Moderate] Screen 1's menu ordering diverges from the demo.** `Identify` renders before `Challenge` (demo: after), and the "Scene actions … show here once a scene is running" line renders between `Challenge` and `Mute`/`Block` rather than trailing the whole menu (demo: last line). Root cause: `PersonaMenuGroupKey`'s declared order (`perception, conflict, scene, social`, `src/actions/constants.py:202-208`) puts `identify` in the same group as `Look`/`View sheet` (rendered together, ahead of the group loop) and puts the `scene` group's empty-state ahead of `social`. Not a data-content bug — the same information is present, just placed differently than the approved design, which specifically positioned the footer as the menu's closing explanation.
- **[Minor] Screen 1b drops the approved "how others see you" hint copy** on the self-Look row. `grep -rn "how others see you" src/ frontend/src/` returns nothing anywhere in the repository — this is copy the demo shows and ratified copy that was never carried into the implementation, not a wording variance.
- **[Minor] Screen 2/2b's Look body collapses its Status/Wearing/Markings sections into one run-on paragraph** instead of the demo's separate labelled lines, because `LookDialog.tsx:80` renders the `\n`-joined text through `FormattedContent` without `whitespace-pre-wrap` — the convention every other freeform-text reader in this codebase follows (e.g. `ExplorationReader.tsx:138`, `ObjectsList.tsx:118`).

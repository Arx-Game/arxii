- Comparison notes: One unresolved divergence. The demo's hit roll result row reads Hit, good with the right-hand note then the damage roll, set in the same two-column row layout as every other roll row. The build's result row (RollBreakdownCard.tsx, the last div inside the ruled list) renders the result text alone, so the approved note never appears, on a hit or anywhere (last-outcome-card-desktop-dark.png). The note is only true after a hit (a miss ends the Strike, last-outcome-miss-desktop-dark.png), so the fix is to show it on a Hit result only. Justified divergences, not defects. (a) The Maneuver chip is not in the action row because maneuvers keep their existing section below. (b) Strike declares at round resolution instead of instantly, so the build shows a Strike confirm button, the Striking Bandit badge once declared, a You ready a strike line in telnet, and the roll rows in the Last Outcome card after the round resolves instead of in the pick leaf. (c) A bare hands chip is offered, as the demo intro allows fists. (d) The skill rating number beside Melee Combat and the stat row's wording stand on the #4844 ruling that the breakdown shows the attacker's terms, and on the slice's own statement that the stat is the strike skill's default. (e) Weapon chips use the catalog's names (one-handed melee, Melee Combat, Thrown Attack) where the demo uses shortened example words, and the roll heading uses the real opponent name. (f) The demo's styling (serif small caps, mono notes, paper palette) is a mock leaf; the build follows the combat rail's tokens in both themes. Observation, not a demo element: loading a round where a Strike is already declared shows the Your action row with nothing selected; the Striking Bandit badge appears once the Strike chip is clicked (turn-declared-desktop-dark.png, turn-strike-declared-badge-desktop-dark.png). The demo draws no declared state, so this is a scope question for the human. The orange Striking badge in light theme is pale (turn-strike-declared-badge-phone-light.png) but follows the repo's existing declared badge classes. Rendering reaches the page: the build is Tailwind utilities from the app's own bundle, and every element rendered styled in both themes. Out of scope and correctly absent: the style row and style skill (slice 2), the lapse (Screen 5), natural weapons (slice 4), vow picks (Screens 3, 7, 8, 9).
- Tested interactions: Picked the Strike chip (Focused Action card), saw the With row and a disabled Strike button; picked the Bandit target, the button enabled; clicked Strike and read the dispatch body (combat_strike with opponent_id and weapon_id of the first weapon, the Rapier). Loaded an already-declared round and clicked Strike to see the badge. Loaded the panel with technique chips to see Strike lead the row. Loaded the post-resolution encounter and read the Last Outcome card for a hit with damage, for a miss, and for a Fine-quality rapier. Typed strike bandit with Rapier through the real telnet command handler and read the declare, hit and miss lines.
- Fixture/live boundary: Live: the REST payloads (encounter, consequence outcomes, strike weapons, roll breakdowns) and the telnet lines come from the real application code on a Postgres test database. Forced: the hit and damage roll outcomes (Critical Success and Success for the hit, Failure for the miss). Fixture: the Rapier's and Throwing knives' names, the test check setup (Melee Attack, Unarmed Attack), and the two technique chips in the technique-row screenshots (static fixture actions in the shape the ActionDeclarationCard tests use). The Playwright page intercepted the browser's API calls and served the recorded payloads, and answered the dispatch POST with success, so no server ran during the screenshots. Not rendered live: a full web session through a running game.
